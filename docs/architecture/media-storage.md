# Media Storage Contract

Status: **foundation design**
Date: 2026-09-25

Mediarama owns this contract. Flysystem is an infrastructure implementation detail.

## Goals

The application must work with:

- local filesystem storage;
- S3-compatible object storage;
- temporary/resumable uploads;
- immutable originals;
- regeneratable derivatives.

Domain/application code must not construct filesystem paths, bucket URLs or CDN URLs.

## Object identity

A stored object is identified by:

```text
StorageObjectId
- disk
- key
```

Example:

```text
disk: media
key: originals/0199.../source
```

The original filename is metadata and is never the canonical object key.

## Required operations

Conceptual PHP interface:

```php
interface MediaStorage
{
    public function write(StorageObjectId $id, readable-stream $stream, WriteOptions $options): StoredObject;
    public function read(StorageObjectId $id): readable-stream;
    public function exists(StorageObjectId $id): bool;
    public function stat(StorageObjectId $id): StoredObject;
    public function delete(StorageObjectId $id): void;

    public function temporaryUrl(StorageObjectId $id, DateTimeImmutable $expiresAt): ?Uri;
    public function publicUrl(StorageObjectId $id): ?Uri;

    public function promote(StorageObjectId $temporary, StorageObjectId $permanent): StoredObject;
}
```

The actual PHP syntax/types will be implemented after the Symfony skeleton exists.

## StoredObject

Return metadata should include:

- object ID;
- byte size;
- checksum where available/verified;
- content type where storage records it;
- ETag/provider metadata as infrastructure-only optional data.

## Key policy

Keys are generated by Mediarama, not users.

Proposed logical layout:

```text
temporary/{upload-session-id}/source
originals/{media-id}/source
derivatives/{media-id}/{processing-version}/{profile}
imports/{import-run-id}/...
```

Do not encode:

- usernames;
- collection names;
- media titles;
- original filename;

into canonical keys.

## Local adapter

The local adapter:

- writes below a configured media root outside application source code;
- prevents traversal outside that root;
- uses streaming IO;
- creates directories as required;
- writes temporary content safely before promotion;
- never exposes an arbitrary local path to templates.

For public delivery, the deployment can choose:

- application-controlled download;
- web-server alias for explicitly public derivatives;
- generated URL through a configured delivery base.

Originals may remain private even when a derivative is public.

## S3-compatible adapter

The S3 adapter:

- supports configurable endpoint/region/bucket;
- does not assume AWS-hosted S3;
- supports private objects;
- can create presigned URLs;
- can use multipart upload for large assets;
- treats copy+delete promotion semantics carefully because object stores do not provide filesystem rename.

The application must not rely on atomic rename being available.

## Upload temporary storage

An upload session owns a temporary key.

Finalization:

1. verify session ownership/authorization;
2. verify received byte count;
3. compute/verify checksum;
4. inspect content;
5. create MediaAsset identity;
6. promote/copy temporary object to immutable original key;
7. commit persistence/state transition;
8. schedule cleanup if any later step fails.

Finalization must be idempotent.

## Immutable originals

After an original reaches its permanent key:

- normal media edits do not overwrite it;
- rotation/orientation normalization creates derivatives;
- watermarking creates derivatives;
- title/filename edits change metadata only;
- reprocessing never mutates it.

Explicit original replacement is a separate future operation with audit/version semantics, not an ordinary write.

## Derivatives

Derivative keys are deterministic from:

- media ID;
- processing version;
- derivative profile.

This enables retry-safe processing.

Explicit regeneration never overwrites the currently published derivative identity. It allocates the next image processing version under a per-media advisory lock, writes the new deterministic versioned objects, and only then publishes the complete derivative-record batch transactionally. Existing versioned derivative keys remain immutable/cache-safe from the public consumer's perspective.

A successful retry may detect the same valid object and avoid duplicate database records.

### Superseded derivative retention

Superseded generations are not deleted immediately after regeneration.

The accepted default retention policy in ADR-0013 keeps the newest three generations per media/kind. Only after a generation falls outside that retained set does its 400-day cleanup grace begin. The grace is deliberately longer than the current one-year immutable public cache lifetime and is not measured from the old generation's creation date.

`mediarama:media:cleanup-derivatives` is preview-only by default. `--execute` transactionally converts eligible derivative records into durable storage-cleanup jobs before physical deletion is attempted.

The cleanup boundary never scans arbitrary storage. Eligible keys must remain inside the deterministic `derivatives/{media-id}/v{version}/...` namespace or the transaction aborts.

## Checksums

Mediarama calculates SHA-256 for originals during ingestion.

Use cases:

- integrity;
- import reconciliation;
- potential duplicate detection;
- retry verification.

Duplicate detection policy is separate: equal checksum does not automatically mean the user intended one logical asset.

## URLs

URLs are delivery artifacts, not persistence identity.

The storage/delivery infrastructure can return:

- no URL (stream through application);
- public URL;
- temporary signed URL.

Templates/controllers receive authorized delivery URLs only after access policy evaluation.

## Delete semantics

SQL state changes first.

Physical object deletion is performed by retryable background cleanup after the relational transaction commits.

This applies to:

- deleted media;
- obsolete derivatives;
- abandoned uploads;
- failed imports;
- orphan detection.

A failed storage delete is operational debt, not a reason to resurrect a database entity.

For superseded derivatives and failed-generation orphans, that operational debt is persisted in `storage_cleanup_jobs`. Claims are retryable; stale claims can be reclaimed; an already-missing object is an idempotent success. This means a process may stop after the database transaction, during storage deletion, or after physical deletion without losing the reconciliation path.

## Orphan cleanup

Scheduled maintenance must detect:

- expired upload sessions;
- temporary keys with no active session;
- derivative records missing objects;
- known Mediarama object keys with no database ownership where safely detectable.

Never blindly delete unknown objects from a shared bucket/prefix.

## Storage contract tests

The same contract suite must run against:

- local adapter;
- S3-compatible test adapter/environment.

Test:

- stream round trip;
- Unicode original metadata independent of key;
- exists/stat;
- delete;
- promotion;
- idempotent operations;
- missing object behavior;
- URL behavior;
- large streaming content;
- traversal protection for local storage.
