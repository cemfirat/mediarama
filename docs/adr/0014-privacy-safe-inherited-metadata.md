# ADR-0014: Rebuild Privacy-safe metadata from an explicit allowlist

- Status: **Proposed**
- Date: 2026-09-27
- Tracks: #87
- Related: #68, #88, ADR-0013

## Context

Mediarama generates ordinary metadata exports by copying source bytes and editing metadata in the copy.

That is desirable because the immutable source remains untouched and image pixels are not recompressed. It also means inherited metadata survives unless explicitly removed.

A denylist is insufficient for a durable Privacy-safe contract:

- EXIF contains owner names, serial numbers and unique identifiers;
- IPTC/XMP contain creator/contact/person/location/rights-party identifiers;
- XMP may contain namespaces Mediarama does not normalize;
- PNG permits arbitrary textual metadata;
- vendor/private metadata may carry identifiers outside Mediarama's canonical model.

At the same time, blindly removing all metadata is not format-neutral. Color-management and orientation/container state may be required for faithful display, and TIFF/QuickTime-family image containers have structural differences from JPEG.

ExifTool itself documents this distinction.

## Proposed decision

### Product policy and storage mechanics are separate

Privacy-safe has one product guarantee, but its physical metadata scrub may be format-specific.

The generated artifact must not inherit arbitrary privacy/user metadata merely because Mediarama does not know that tag.

### Embedded generated copies

Move from a growing sensitive-tag denylist toward an allowlist/rebuild boundary:

1. begin from a generated byte copy, never the immutable source;
2. remove inherited user/privacy metadata using a format-proven strategy;
3. retain only reviewed rendering-critical state required for faithful display;
4. write the canonical fields intentionally retained by Privacy-safe;
5. verify the result through real-file read-back.

Rendering-critical state is infrastructure, not a user metadata opt-in.

Candidate state requiring explicit evidence includes:

- ICC/color-space information;
- image orientation;
- PNG color/gamma semantics;
- AVIF/HEIC rotation, mirroring and color representation;
- required container/image structural data.

### RAW

Do not apply embedded-copy scrubbing to proprietary RAW originals.

Mediarama continues to create a fresh XMP sidecar from canonical metadata policy output. The RAW original is never destructively rewritten.

### Fail closed

If a format cannot yet prove both:

- sensitive inherited metadata is removed; and
- rendering-critical behavior is preserved,

then the stronger Privacy-safe generated-copy guarantee should be unavailable for that format instead of silently falling back to a weaker denylist.

### User-facing wording

Do not call the artifact fully anonymous.

Privacy-safe may intentionally retain visible canonical descriptive values. If fields such as title, description, creator or copyright remain, UI/export wording must say so because free-form text may itself contain personal information.

## Why an allowlist

A denylist must know every sensitive field in advance. The metadata ecosystems used by JPEG/TIFF/PNG/WebP/AVIF/HEIC do not provide such a closed set.

An allowlist instead makes the retained surface reviewable.

## Why this ADR remains Proposed

The exact format-specific preservation commands are not accepted merely from documentation.

Before acceptance, CI evidence must exercise the production path against all declared writable embedded-copy formats and seed representative sensitive metadata plus rendering-critical metadata.

The required evidence is defined in:

`docs/research/privacy-safe-inherited-metadata-audit.md`

## Consequences if accepted

Positive:

- unknown inherited metadata no longer survives by default;
- Privacy-safe has a reviewable retained-metadata surface;
- future vendor namespaces do not silently weaken the guarantee;
- RAW remains protected from unsafe destructive scrubbing;
- Custom can later reuse the same scrub foundation to make field selection authoritative (#88).

Costs:

- metadata scrubbing becomes format-aware;
- real-file regression fixtures become part of the security/privacy boundary;
- some formats may temporarily fail closed if faithful scrub semantics cannot be proven;
- rendering-critical metadata must be explicitly classified and maintained.
